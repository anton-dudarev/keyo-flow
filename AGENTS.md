# AGENTS.md — Keyo

## 1. О проекте

**Keyo** — утилита для записи, редактирования и воспроизведения действий пользователя (мышь и клавиатура). Текущая реализация работает на Windows.
Базовый функционал (MVP):

- Перехват глобальных событий ввода (движение, клики, скролл, нажатия/отпускания клавиш).
- Сохранение и загрузка сценариев (макросов) в формате JSON.
- Воспроизведение сценариев с настройкой скорости и количества повторов.
- Глобальные горячие клавиши для старта/остановки записи и аварийного прерывания (Kill-Switch).
- Графический интерфейс для управления сценариями и настройками.

## 2. Стек и команды

- **Язык / Фреймворк:** Rust (edition 2021).
  - *Эмуляция и перехват в Windows:* Win32 API через `windows-sys`, низкоуровневые хуки и `SendInput`.
  - *Графический интерфейс (GUI):* `egui` (с бэкендом `eframe`).
  - *Сериализация:* `serde`, `serde_json`.
- **Сборка:** `cargo check --features gui` (разработка) / `cargo build --release --locked --features gui --bins` (релиз).
- **Запуск тестов:** `cargo test --locked --features gui --lib` (запускать только модульные тесты, изолированные от реальной ОС).
- **Линтер / Форматтер:** `cargo clippy --locked --features gui --all-targets -- -D warnings` и `cargo fmt --check` (предупреждения Clippy считаются ошибками).

## 3. Архитектура проекта

Код разделён на слои. Рабочие потоки передают статусы и результаты в GUI через каналы `mpsc`. Функции внутри слоёв и между слоями могут вызываться напрямую.

- `src/platform/` — низкоуровневые обертки над хуками ОС и эмуляцией.
- `src/core/recorder.rs` — расчет относительных задержек, фильтрация шума, генерация событий.
- `src/core/scenario.rs` — типы сценариев, событий, клавиш и скан-кодов, базовые проверки и операции над строками.
- `src/core/timeline.rs` — объединение записанных событий в удержания и траектории, разворачивание составных событий для редактора и воспроизведения.
- `src/core/timing.rs` — воспроизводимый разброс задержек и длительностей удержаний.
- `src/core/player.rs` — движок воспроизведения в отдельном потоке. Должен использовать точные `std::time::Instant` для компенсации дрейфа таймингов.
- `src/core/safety.rs` — освобождение зажатых сценарием клавиш и кнопок мыши. Аварийная остановка Windows находится в `src/platform/windows.rs` и `src/platform/windows/corner.rs`.
- `src/storage/` — сериализация/десериализация сценариев.
- `src/ui/` — окна и виджеты на базе `egui`. UI-поток **не должен** блокироваться логикой записи или воспроизведения.

## 4. Критические правила для ИИ-агента (Guardrails)

1. **Разделение потоков (Threading):** `eframe` (egui) требует запуска в главном потоке. Логика перехвата ввода (глобальные хуки Win32) и цикл воспроизведения (`player`) ОБЯЗАНЫ запускаться в отдельных `std::thread` и обмениваться сообщениями с UI через неблокирующие каналы (`std::sync::mpsc` или `crossbeam_channel`).
2. **Запрет на реальный ввод в тестах:** Никогда не используй реальные вызовы эмуляции или хуков в тестах. Логика расчета времени и координат должна тестироваться на моках (чистых функциях).
3. **Гарантированный сброс клавиш:** Любой цикл воспроизведения должен реализовывать паттерн Drop или аналог `try-finally`, который принудительно отжимает модификаторы (`Ctrl`, `Shift`, `Alt`, `Meta`) в случае прерывания (Kill-Switch) или ошибки.
4. **Изоляция Kill-Switch.** Сигнал экстренной остановки (например, `Esc`) должен прерывать ожидание следующего события. Поток воспроизведения использует атомарный флаг и пробуждается через `unpark`. Windows-адаптер проверяет сигнал в цикле обработки сообщений.
5. **Точность таймингов:** Использовать только `Instant::now()` для замеров времени. Никогда не использовать системное время (`SystemTime`) для расчета задержек (`duration`), так как оно подвержено сдвигам (NTP).
6. **Координаты:** Учитывай DPI монитора. Сценарии версии 2 используют физические пиксели виртуального рабочего стола, а версии 3 — координаты клиентской области окна в миллионных долях. Windows-бэкенд преобразует их в абсолютные координаты `SendInput`. В `egui` координаты могут быть логическими.

## 5. Версии и релизы

- Версия приложения задаётся в `Cargo.toml` как `MAJOR.MINOR.PATCH`. Версия JSON-формата сценариев управляется отдельно.
- До `1.0.0` исправления повышают `PATCH`, а новые возможности и несовместимые изменения повышают `MINOR` со сбросом `PATCH` в ноль. Выпускай `1.0.0`, когда проект готов заявить стабильную совместимость. Начиная с `1.0.0`, несовместимые изменения повышают `MAJOR`, совместимые новые возможности повышают `MINOR`, а совместимые исправления повышают `PATCH`. При повышении разряда сбрасывай младшие разряды в ноль.
- Добавляй заметные пользователям изменения в раздел `Unreleased` файла [CHANGELOG.md](CHANGELOG.md).

Порядок выпуска:

1. Обнови версию в `Cargo.toml`, запусти `cargo check` для обновления `Cargo.lock` и проверь, что версия пакета в обоих файлах совпадает.
2. Перенеси записи из `Unreleased` в раздел новой версии с датой выпуска. Оставь пустой раздел `Unreleased` наверху.
3. Запусти `cargo test --locked --features gui --lib`, `cargo clippy --locked --features gui --all-targets -- -D warnings` и `cargo fmt --check`.
4. После успешных проверок закоммить файлы релиза и поставь на этот коммит аннотированный тег командой `git tag -a vX.Y.Z -m "Release vX.Y.Z"`, подставив версию из `Cargo.toml`.
5. Собери релизные `keyo-gui.exe` и `keyo-cli.exe` для Windows x64. Упакуй их вместе с README, CHANGELOG и демонстрационным `scenario.json` в `keyo-vX.Y.Z-windows-x64.zip`. Проверь, что файлы в архиве совпадают с исходными.
6. Для публикации на GitHub отправь тег, создай релиз с заметками из нужного раздела CHANGELOG и приложи ZIP. Перед публикацией сравни SHA-256 загруженного архива с локальным. После публикации проверь, что релиз и ссылка на ZIP доступны.
